# How does the project-os mod reach each repo: generated by the template sync like the agent files, or installed from a plugin marketplace?

## Problem

The project-os mod in [[FEAT-0041-Project-Os-Mod]] has to reach all the fleet repos and stay current there. A mod always lives inside a Claude Code plugin, so the question is how that plugin is placed and loaded in each repo. Cockpit PHASE-046 suggested making project-os a plugin marketplace, so that project-os's Claude Code files would carry a version instead of being copied once. That suggestion rested on a premise that was already out of date.

## What is true today

- The template sync already refreshes `.claude/`. After a sync, `sync-project-os.py` runs `generate-adapters.py --install-hooks`. That rewrites `.claude/agents/` and `.claude/skills/` and registers the hooks in `.claude/settings.json`. `tools/sync/MANIFEST.yaml` marks both folders `generated`. This has been so since 2026-07-18 (project-os `7ffb5d5`).
- project-os-cockpit's CLAUDE.md ("Model routing") said the sync "never touches `.claude/`", and the 2026-10-08 review and this repo's reply on 2026-10-14 repeated it. It was stale and was corrected on 2026-10-14. Drift is already detected: `generate-adapters.py --check` runs at pre-commit and in CI.
- Checked on 2026-10-14: in the seven repos that have `.claude/agents/`, `planner.md` and `independent-reviewer.md` are byte-identical to the template's. The only differences in `.claude/skills/` are the repos' own skills: `cockpit-driving` in project-os-cockpit, and five iOS skills in your-trainer.

## The options

- **(a) The sync generates the plugin.** `generate-adapters.py` writes the plugin folder the way it writes the agent files, and registers it. Nothing is renamed, and no repo needs a new install step. Not yet checked: whether `.claude/settings.json` can load a plugin from a folder inside the repo without a marketplace. If it cannot, `CLAUDE_CODE_PLUGIN_DIRS` or a local marketplace entry would be needed.
- **(b) A marketplace carrying only the mod.** The mod carries a version and updates without a sync. The skills and agent files stay generated.
- **(c) A marketplace carrying everything.** Plugin skills are named `plugin:skill`, so every instruction, `CLAUDE.md` line and hook message that names a skill would need checking. A repo's own skills (the six above) would stay local files, so a repo would have two kinds of skill name. Codex does not load Claude Code plugins, so the Codex adapter keeps its current files either way.

## Decision (2026-10-14)

**Option (a).** FEAT-0041 started on 2026-10-14, when Edwin chose in project-os-cockpit to build it before cockpit FEAT-0157 ("Build FEAT-0041 too"). The mod cannot reach a session outside a cockpit terminal without some way of loading, so the minimum of this issue is part of FEAT-0041 and is built as [[TASK-0199-The-Mod-Reaches-Every-Repo-Through-The-Template-Sync|TASK-0199]]. The planning session took option (a), as recommended above: it renames nothing, needs no marketplace, and needs no ADR. Edwin may overturn it.

One fact found at planning: `claude plugin marketplace add` takes `--scope project`, which declares a marketplace in the repo's own `.claude/settings.json`. Whether a person must still confirm an install once per machine is checked live in [[TASK-0198-Two-Plugins-Share-The-Line-Above-The-Prompt-Checked-Live|TASK-0198]].

## How a repo loads the mod: checked live (TASK-0198, Claude Code 2.1.300, 2026-10-14)

**Option (a) works, through a marketplace that lives inside the repo and has a name unique to that repo.** Checked in two throwaway git repos in a real terminal session.

- **A repo's settings cannot name a plugin folder directly.** Setting `CLAUDE_CODE_PLUGIN_DIRS` in the `env` block of `.claude/settings.json` is ignored. Claude Code logs: "CLAUDE_CODE_PLUGIN_DIRS in .claude/settings.json is ignored — project-scoped settings can't set this key. Set it in ~/.claude/settings.json or managed settings instead."
- **A marketplace declared by the repo does work, with a relative path.** The repo holds `.claude-plugin/marketplace.json`, which lists the plugin by a path inside the repo. `.claude/settings.json` carries two keys:

  ```json
  {
    "extraKnownMarketplaces": { "<name>": { "source": { "source": "directory", "path": "./" } } },
    "enabledPlugins": { "<plugin>@<name>": true }
  }
  ```

  `claude plugin marketplace add --scope project ./` writes an absolute path there. A relative `"./"` written by hand works the same, and only that form can be committed to a template.
- **Nobody has to install anything.** On the first session in the repo, Claude Code registers the marketplace in the background, and the plugin draws in that same session. No prompt appeared beyond the folder-trust question Claude Code asks of any new folder.
- **The plugin runs from the repo's own folder, not from a copy.** The debug log says `Loading plugin t198-a from source: "./tools/claude-plugin/t198-a"`, and nothing was written to `~/.claude/plugins/cache` or `installed_plugins.json`. An edit to the folder showed in the next session with no version change. So a template sync that rewrites the folder updates what runs.
- **The marketplace name must be different in every repo.** Claude Code records each marketplace once per machine, in `~/.claude/plugins/known_marketplaces.json`, by name, with the absolute path of the repo that registered it. A second repo declaring the same name loaded the first repo's copy of the plugin, and only then re-pointed the name at itself ("Marketplace 't198-local' exists with different source — overwriting"). With twelve repos open, each session would run whichever repo's copy was registered last. With a name of its own, the second repo loaded its own copy. TASK-0199 therefore generates a name per repo, for example `project-os-<repo folder name>`.
- **Renaming a marketplace needs its old registration removed.** A folder already registered under one name was skipped under a new one ("Source already materialized as 't198-local', skipping clone"). This only matters if a name is ever changed.
- **A `.ts` or `.tsx` hooks module runs with no Node toolchain in the repo.** The scratch plugins had no `package.json` and no `node_modules`.
- **A hook can run `git` and `python3`.** `$.process.run(["git", "status", "--porcelain"])` and `$.process.run(["python3", "-c", "print(42)"])` both returned exit code 0 with their output. It takes one argv list; a command and a separate argument list are refused.
- **The cockpit's plugin and a repo's plugin load together.** In a repo with its own marketplace plugin, a session that also had `CLAUDE_CODE_PLUGIN_DIRS` set, as a cockpit terminal does, loaded both and drew the joined line.

Everything the check registered on this machine was removed afterwards: both scratch marketplaces, the one install made with `claude plugin install`, and its cache folder.
